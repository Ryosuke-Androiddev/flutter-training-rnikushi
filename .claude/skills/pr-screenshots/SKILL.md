# pr-screenshots

UI に変更がある PR に、iOS / Android の Before / After 画像を載せるまでの流れをまとめたスキルです。
手順の中心は `scripts/pr_screenshots.py` です。デバイスの検出、スクショ、ビルドと起動、画像のアップロード、PR 本文の更新を受け持ちます。

```sh
S=.claude/skills/pr-screenshots/scripts/pr_screenshots.py
```

## 全体の流れ

1. 準備（PR・デバイス・ファイル名の接頭辞を決める）
2. Before のスクショ（**ビルドしない**）
3. 変更をビルドして起動する
4. After のスクショ
5. 画像を確認する
6. PR に添付する

ユーザーが「Before だけ」「添付だけ」のように一部だけを頼んだ場合は、その手順だけを行います。

## 1. 準備

- **PR**：現在のブランチの PR を使います（`gh pr view --json number,url`）。PR がまだなければ、作成するか、番号を指定してもらうかをユーザーに確認します。
- **デバイス**：起動中のものだけを使います。`xcrun simctl list devices booted` と `adb devices` で確認します。片方しか起動していなければ、その OS だけで進め、そのことを報告します。デバイスを勝手に起動しないでください。どの機種で撮るかはユーザーが決めることです。
- **接頭辞（`--prefix`）**：Desktop のファイル名と、`pr-assets` ブランチ上のフォルダ名になります。研修の課題なら `session1` のように Session の番号を使い、それ以外なら `pr-<PR番号>` を使います。同じ接頭辞で撮り直すと、画像は上書きされます。

## 2. Before のスクショ

```sh
python3 $S capture --phase before --prefix session1
```

- **このステップの前にビルドしないでください。** Before は「変更前の画面」なので、デバイスで動いている今の状態を撮ることに意味があります。先にビルドすると、変更後の画面に置き換わってしまい、取り返しがつきません。
- 撮る前に、アプリが前面に出ているか、目的の画面が表示されているかを確認します。アプリが閉じていたら、ビルドせずに起動だけします（`python3 $S launch --no-build`）。
- デバイスに入っているアプリが変更前の状態か分からない場合は、撮る前にユーザーに確認します。例えば、すでに変更をビルド済みかもしれない場合です。必要なら、main をビルドしてから撮るよう提案します。

保存先：`~/Desktop/<prefix>_before_ios.png`、`~/Desktop/<prefix>_before_android.png`

## 3. 変更をビルドして起動する

```sh
python3 $S launch
```

Android は debug APK をビルドしてインストールし、起動します。iOS は Simulator 用にビルドしてインストールし、起動します。2回のビルドには数分かかるので、タイムアウトは長め（10分程度）にしてください。

`flutter run` を使わず、インストールして起動するだけなので、ホットリロードはできません。ユーザーがホットリロードで確認したい場合は、`fvm flutter run -d <device>` のコマンドを案内します。

## 4. After のスクショ

```sh
python3 $S capture --phase after --prefix session1
```

## 5. 画像を確認する

Read ツールで4枚すべてを開き、次の点を確認します。

- Before が変更前、After が変更後の画面になっているか
- アプリが前面に出ているか（ホーム画面・ダイアログ・キーボードが写り込んでいないか）
- 起動の途中（真っ白な画面など）を撮っていないか。この場合は少し待ってから撮り直す

問題があれば撮り直します。添付してしまうと取り消しが面倒なので、この確認は先に済ませます。
ユーザーが「動作確認させて」と言っている場合は、ここで一度止めて結果を報告します。添付するかどうかは、ユーザーの指示を待ちます。

## 6. PR に添付する

```sh
python3 $S attach --prefix session1 --ios-label "iOS（iPhone 17）" --android-label "Android（Emulator）"
```

- 画像は `pr-assets` ブランチの `<prefix>/` にアップロードします。このブランチは main とつながりのない画像専用のブランチで、merge はしません。ブランチがなければ作成し、あれば追記します。
- PR 本文の `## UIの変更` 節を、次の表に置き換えます。節がなければ、末尾の `🤖 Generated with ...` の直前に追加します。
  ```
  | Before | After |
  | :---: | :---: |
  | <img src="..." width="200"> | <img src="..." width="200"> |
  ```
  この形式はプロジェクトの PR テンプレート（`.github/pull_request_template.md`）に合わせています。行は iOS、Android の順で並べ、表の上に「上段 / 下段」がどの OS かを1行で書きます。
- `--ios-label` / `--android-label` には、実際の機種名を入れます。iOS は `xcrun simctl list devices booted` の名前を使います。

### アップロードの方法について
- GitHub のブラウザ添付（`user-attachments`）は、gh や API ではアップロードできません。そのため、この方法を使っています。
- 画像の URL は、ブランチ名ではなくコミット SHA を固定した URL にしています。撮り直しても過去の PR の画像が置き換わらず、キャッシュの古い画像が表示されることもありません。
- リポジトリが public なら、画像も公開されます。スクショに個人情報やトークンなどが写っていないかを、手順 5 で確認してください。
- `pr-assets` のコミットは API で作るため署名なしになりますが、main には merge しないのでマージ条件には影響しません。また、`pr-assets` は削除しないでください。削除すると、過去の PR の画像が表示されなくなります。

## うまくいかないとき

- **Android のスクショが壊れる**：エミュレータに複数のディスプレイがあると、`adb exec-out screencap` の出力に警告文が混ざります。スクリプトはデバイス上に一度保存してから取り出す方式なので、この問題を避けられます。
- **このセッションが worktree に隔離されている場合**：`git/blobs` を含むような長いワンライナーは、ガードに拒否されることがあります。スクリプトをそのまま呼べば問題ありません。
- **ビルドが失敗する**：エラーの内容をユーザーに報告して止まります。Before は撮影済みなので、修正後に手順 3 から再開できます。

## 報告

最後に、次の内容をユーザーに伝えます。

- Desktop に保存したファイルのパス
- 添付先の PR の URL
- 撮らなかった OS とその理由（デバイスが起動していなかった、など）
